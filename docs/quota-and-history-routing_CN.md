# 配额隔离与不可回放会话选路

## 结论

明确的配额耗尽应进入账号限流，立即退出新请求和续传调度。不能回放的历史必须在选号前锁定上游；收到 BPS 拒绝后，不应再尝试无法成功的原生切换，也不应把原错误覆盖成“切换历史不兼容”。

2026-09-25 的线上抽样已经存在 18 个限流账号。因此连续出现本地 429 不代表这些账号还在被调度：同一 Key 的分组、目标模型、上游能力和原生 State 条件取交集后，剩余账号可能都没有额度。其他账号显示 active，也不代表能服务这个请求。

## 错误与隔离范围

| 证据 | 隔离范围与处理 | 恢复依据 |
| --- | --- | --- |
| `usage_limit_reached`，或精确的 `insufficient_quota` / `quota_exhausted` 等结构化 code/type | 官方 OAuth 账号进入权威配额冷却；两条路径和续传均跳过 | 优先使用明确的重置时间或耗尽窗口 |
| 通用配额/账单错误没有重置信息 | 账号冷却 30 分钟后允许重新检查，不把这个时间宣称为套餐恢复时间 | 后续真实成功、管理员处理或重新检查 |
| 订阅窗口耗尽但缺少时间 | 保留既有套餐兜底：free 7 天，其余 5 小时 | 既有用量探测与窗口恢复机制 |
| 普通 429 / `rate_limit_exceeded` | 账号短冷却；保留现有 15 秒起步、最高 5 分钟退避及上游 Retry-After | 短冻结到期，避免并发错误不断滑动窗口 |
| Spark 独立用量窗口耗尽 | 只限制 Spark；明确的通用账单/配额耗尽仍限制整个账号 | Spark 重置或账号恢复 |
| 模型套餐不支持、模型容量不足 | 只限制该账号的具体模型；保留既有模型冷却策略 | 模型冷却或新的能力证据 |
| BPS `403: This request was blocked by our usage policy.`，code=null | 不推断为配额耗尽、永久无能力或封号；只在原有严格规则下允许可回放请求切换 | 原始响应及后续强测试证据 |
| 明确内容安全/网络安全策略拒绝 | 保持现有安全处理；本次没有增加绕过或扩大切换条件 | 不以换路径规避策略 |
| 401、工作区停用、传输 EOF | 保持各自鉴权、工作区和网络处理，不混入配额分类 | 对应问题的实际修复 |

结构化配额识别只读取错误对象的 code/type，按完整值匹配，不扫描用户输入，也不因错误 message 提到 quota 就持久隔离账号。中转、Grok、Antigravity 保留各自的状态处理方式。

已经生效的较长权威配额冷却，不能被后到的较短 5h 错误、短时 429 或 WHAM 观察覆盖。并发更新通过用量观察锁串行化，调度索引在状态写入后刷新，数据库记录同样保留最终期限。

## 会话选路

1. 正常化请求完成后、选号前检查历史。`previous_response_id`、加密 reasoning/compaction、item reference、加密 agent 消息和不完整工具调用都禁止自动跨上游。
2. 有历史来源证据时，使用产生该历史的实际路径。没有来源证据的旧历史，保持当前策略的首选路径并关闭自动切换；不猜测密文兼容性。
3. 普通 HTTP、SSE、WebSocket 和 compact 共用这套决定。单个请求的重试不能解除路径锁；同路径换号仍受既有账号、分组、能力、模型、State 和续传约束。
4. 完整明文、完整配对的工具历史继续允许原有受控切换。已经输出内容、明确安全拒绝、超出尝试预算等条件仍禁止切换。
5. BPS 403 遇到不可回放历史时，保留原始错误语义和既有标准错误 code，日志增加 `switch_blocked=history_not_replayable`；不再制造一次失败切换及其 503。
6. 首轮安全切换成功后，下一轮如携带该路径的加密历史，会锁定到实际来源。原路径不可用就明确失败，不试另一路。历史来源与 Key 的 only 策略冲突时返回 `codex_route_history_policy_conflict`；混合不兼容来源返回 400 `codex_route_history_conflict`。

来源记录使用下游 Key ID 命名空间及 SHA-256 摘要，值只有路径，不保存明文、密文、Token 或会话原文。它不使用共享 Session-ID 做全局绑定，避免父任务和子代理互相改路。完整明文工具对也不作为强制来源证据，允许合法的历史切换。

来源记录保留 24 小时，每次最多处理 1024 个历史标识，单个观察帧最多 8 MiB。使用现有 memory/Redis 运行态缓存：memory 重启、TTL 到期、记录缺失或缓存故障时，只能按“未知来源、保持首选、不自动切换”处理，无法证明旧密文属于哪条路径。跨实例部署应共享 Redis，并保持会话期间的 Key 策略稳定。未知历史不是兼容性证明。

## 客户端与强测试结果

- 明确配额耗尽在最终 HTTP 响应中返回 429、`rate_limit_error`、`account_pool_usage_limit_reached`，不再改写成 503。保留上游给出的恢复信息。
- SSE/WS 内的明确配额错误也会触发账号限流。WS 即使开启隐藏上游详情，也保留配额错误类别和安全的通用文案。
- 压缩历史的来源仍可用但账号额度耗尽时，优先报告限流，不误报 `compaction_upstream_unavailable`。
- 账号内部保留 `responses_rate_limited` 原因，后台归入限流。BPS 强测试会跳过这类账号，结果显示 `rate_limited`、attempts=0，不把配额不足记成新的能力失败。
- 单次上游拒绝与整个授权候选池耗尽是不同层次；不能把路径尝试数量和最终失败请求数量相加。

- [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)，参考提交 `9eed67b182741a6ed3559143056a9c3b35e85bf5`：参考 `sdk/cliproxy/auth/conductor_cooldown.go` 的账号/模型作用范围及不缩短已有配额期限；参考 WebSocket executor 对需要重放状态的失败处理。
- 本项目已有双上游能力记录、Key 分组权限、原生 State、并发租约、Spark 窗口、跨实例冷却和错误重试机制。本次修补这些机制之间的边界，避免另建一套账号池状态。

## 验证与运维边界

回归覆盖结构化配额错误的 HTTP 400/403/429/500 和 SSE/WS 失败、续传不得绕过配额、数据库冷却持久化、并发较短期限覆盖、强测试跳过限流账号、不可回放请求零调用另一上游、跨请求真实路径保持、Key 隔离/策略冲突、混合来源、长压缩状态、可移植工具对，以及压缩历史的 WS 限流错误。

另一个已经确认的线上原因是 3proxy 每 20 分钟被计划任务重启；21:00:05 的集中 EOF 与重启时间一致。本次代码修改不会解决被外部进程主动断开的连接。该任务应单独检查是否必要，按维护窗口或支持连接排空的方式更新代理，不能通过批量标错账号掩盖它。
